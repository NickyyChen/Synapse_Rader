## 2. 业务背景

### 2.1 行业背景

2025-2026 年 AI 领域进入技术爆发期。多模态大模型、AI Agent、开源工具链每周都有重大更新。GitHub 每天诞生数百个 AI 相关项目，arXiv 每天发布数百篇 AI 论文，HuggingFace 和 ModelScope 上每天涌现新模型。技术迭代速度远超个人追踪能力。

### 2.2 业务痛点

歪麦公司的内部决策者每周需要回答以下问题：

- "这个新模型/框架/路线，值不值得我们投入资源跟进？"
- "竞品在用什么技术？行业主流方向是什么？"
- "上周的某个热点项目现在怎么样了？"

当前团队依赖人工浏览社区、微信群分享、口口相传，存在以下问题：

| 痛点 | 影响 |
|------|------|
| 信息过载 | 每天数百条 AI 资讯，人工无法全覆盖 |
| 噪声过多 | 大量营销软文、学术灌水干扰判断 |
| 评测缺失 | 缺少统一的工程价值评判标准，决策靠直觉 |
| 历史遗忘 | 上周看过的项目记不住细节，无法做时间维度对比 |
| 渠道分散 | GitHub/HF/arXiv/公众号分布于多个平台，切换成本高 |

### 2.3 业务目标

| 目标 | 衡量方式 |
|------|---------|
| 每天 8:00 前自动生成一份经过筛选和评分的 AI 技术情报日报 | 日报按时推送率 ≥ 95% |
| 每条情报包含四个维度的评分（商业潜力、落地难度、性能指标、业务兼容性）和推荐等级 | 所有入库情报 100% 完成评分 |
| 团队每天审阅日报的时间 ≤ 30 分钟（不含深度讨论） | 日报核心结论可 5 分钟读完全文 |
| 历史情报支持按日期/分类/评分/关键词秒级检索 | 检索响应时间 < 1 秒 |

### 3.2 用户场景

**场景 A（技术决策者 — 晨间 5 分钟）**

> 早上 8:00，飞书群收到 Synapse_Rader 日报推送（@all），打开消息。扫一眼概览数字（今日 2 条强推），直接看"强烈推荐"区域，对其中一条 4.5 分的 Agent 框架感兴趣，点击飞书文档链接查看详细分析，转发给技术研究员做深度评估。

**场景 C（系统管理员 — 手动触发）**

> 周一早上 10:00 周会，技术决策者需要最新的情报数据。管理员打开 Web 页面的手动触发，点击"执行日报流程"，看到进度条实时滚动（采集→筛选→分析→报告→分发），3 分钟后完成，日报更新到飞书和 Web。

## 5. P0 功能详细描述

### F-01：多信源自动采集

#### 用户故事

> 作为技术决策者，我希望系统每天自动从主流 AI 社区采集最新动态，不需要我自己去各个网站刷信息。

#### 功能描述

系统在每日 7:00 自动触发，并行访问 4 个信源 API，抓取前一日最新条目。

| 信源 | 采集范围 | 每源数量 | 采集方式 |
|------|---------|---------|---------|
| GitHub Trending | Python 语言、daily/weekly trending | Top 20 | GitHub API + httpx |
| HuggingFace | 每日 Trending models/datasets/spaces | Top 20 | HuggingFace Hub API |
| ModelScope | 魔搭社区热门模型/数据集 | Top 20 | ModelScope 开放 API |
| arXiv | cs.AI / cs.CL / cs.CV / cs.LG（前一日） | Top 20 | arXiv API (feedparser) |

**采集结果：** 4 源共约 60-80 条原始条目，基于 URL + title 的 SHA256 hash 去重后约 50-60 条。

#### 数据流

```
Scheduler (7:00)
  → 并行调用 4 个 Fetcher（4 线程）
  → 去重（SHA256）
  → 写入 raw_items 表（status=pending）
  → 通知 Curator Agent 开始筛选
```

#### 容错设计

- 单个信源 API 调用失败不影响其他信源
- 失败信源记录到 `fetch_errors`，在日报中标注"今日 XX 源采集失败"
- 每个信源的调用结果写入 `execution_logs`

#### 验收标准

- [ ] 每日 7:00 自动触发（误差 ±5 分钟）
- [ ] 4 个信源并行调用，总耗时 < 60 秒
- [ ] 去重准确率 100%（同一 URL+title 不重复入库）
- [ ] 单源失败时其他源正常执行，失败源记录到日志
- [ ] 采集结果通过 `GET /api/report/today` 可见

### F-02：智能筛选与分类

#### 用户故事

> 作为技术研究员，我不希望日报里有大量无关的营销软文和学术灌水内容，只要 AI Agent、多模态大模型、NLP 这三个领域的高质量条目。

#### 功能描述

系统对采集到的 50-60 条原始条目进行三级过滤：

| 层级 | 方法 | 输入量 | 输出量 | 实现 |
|------|------|--------|--------|------|
| L1 关键词过滤 | 标题/摘要匹配关键词列表 | ~60 条 | ~35 条 | Python 规则引擎，毫秒级 |
| L2 LLM 分类 | LLM 判别领域归属 + 打标签 | ~35 条 | ~20 条 | DeepSeek-v4-pro，批量处理 |
| L3 LLM 去噪 | LLM 剔除灌水/营销/无关内容 | ~20 条 | ~15 条 | DeepSeek-v4-pro，批量处理 |

**L1 关键词列表（部分）：**
`Agent` `LLM` `Multimodal` `NLP` `Transformer` `RLHF` `RAG` `MCP` `function-calling` `tool-use` `大模型` `多模态` `智能体` `对齐` `推理` `微调` `预训练` `提示工程`

**分类标签体系：**

| 一级标签 | 二级标签 |
|---------|---------|
| AI Agent | 新模型发布、论文、开源工具/框架、技术路线/观点、数据集、产品动态 |
| 多模态大模型 | 同上 |
| NLP | 同上 |

**淘汰条目标记：**
- `filtered_out_keyword` — L1 关键词不匹配
- `filtered_out_noise` — L3 判定为噪声

#### 验收标准

- [ ] L1 关键词列表可通过配置文件修改，无需改代码
- [ ] L2 分类准确率 ≥ 85%（抽样 100 条人工核对）
- [ ] L3 去噪：灌水/营销文剔除率 ≥ 90%
- [ ] 筛选后的条目在 `raw_items.status=curated`，淘汰条目标记具体原因
- [ ] 日均筛选后条目 10-20 条（控制 LLM 成本）

### F-03：AI 四维评分与分析

#### 用户故事

> 作为技术决策者，我不只想看到"有什么新东西"，我需要系统帮我判断"这个东西值不值得跟"，给出有数据支撑的评分和推荐理由。

#### 功能描述

对筛选后的每条情报，LLM 生成结构化分析报告。策展后的 N 条情报**并行分析**（每条独立无依赖，使用 8 线程并发）。

**分析输出包含：**

| 字段 | 说明 | 示例 |
|------|------|------|
| 一句话总结 | ≤50 字的精炼概括 | "轻量级 Multi-Agent 协作框架，支持 Agent 间动态任务分配，延迟 <100ms" |
| 核心亮点（3 点） | 最重要的技术/商业亮点 | ["10+ Agent 并行协作", "内置记忆共享模块", "GitHub 3 天 5k star"] |
| 技术对比 | 与已有技术的差异 | "相比 AutoGen 的对话驱动，该框架采用共享内存机制，延迟降低 40%" |
| 四维评分 | 每个维度 1-5 分 + 置信度 + 评分理由 | 见下方评分体系 |
| 推荐等级 | 强烈推荐 / 值得关注 / 暂不跟进 / 不推荐 | 见下方等级划分 |

**四维评分体系（基础权重）：**

| 维度 | 默认权重 | 评分标准 |
|------|---------|---------|
| 商业潜力 | 0.45 | 5=解决明确商业痛点且市场热度极高；4=市场热度高、应用场景清晰；3=有一定应用前景；2=应用场景模糊；1=偏学术研究暂无商业场景 |
| 落地难度 | 0.20 | 5=开源完整、文档齐全（含详细 README）、pip/brew 即装即用；4=有代码文档较全、部署成本低；3=有代码但文档不足；2=仅有部分代码或 demo；1=无代码/仅论文 |
| 性能指标 | 0.20 | 5=多项 benchmark SOTA 且经过第三方验证；4=部分指标 SOTA；3=与现有方案持平；2=弱于现有方案；1=无性能数据 |
| 业务兼容性 | 0.15 | 5=与公司现有技术栈和业务方向高度匹配；4=大部分匹配；3=部分匹配；2=需要较大适配；1=不匹配 |

**上下文自适应权重调整：**

LLM 先判断情报类型，然后自动调整权重分布。

| 情报类型 | 权重调整 |
|---------|---------|
| 开源工具/框架 | 落地难度权重 +0.10（0.30），商业潜力 -0.05（0.40） |
| 学术论文 | 性能指标权重 +0.10（0.30），商业潜力 -0.05（0.40） |
| 产品/商业动态 | 商业潜力权重 +0.10（0.55），性能指标 -0.10（0.10） |
| 默认（其他） | 使用基础权重不变 |

**评分公式：**

```
总分 = 商业潜力×W_business + 落地难度×W_deploy + 性能指标×W_perf + 业务兼容性×W_compat
```
W 值根据情报类型动态确定。

**推荐等级划分：**

| 总分区间 | 推荐等级 | 决策建议 |
|---------|---------|---------|
| ≥4.0 | 强烈推荐 | 建议尽快组织深度评估，1 周内给出跟进方案 |
| 3.0-3.9 | 值得关注 | 持续追踪，等待更多信号或更成熟版本 |
| 2.0-2.9 | 暂不跟进 | 定期回顾，暂不投入资源 |
| <2.0 | 不推荐 | 不纳入追踪范围 |

**评分增强机制：**

| 机制 | 说明 |
|------|------|
| 置信度标注 | 每个维度评分附带 0.0-1.0 置信度，表示 LLM 对评分的把握。置信度 <0.6 的维度在报告中标注"⚠️ 低置信度" |
| 解释质量 | 评分理由区分"数据驱动"（引用具体数字/链接）和"主观判断"（泛泛而谈），后端自动标注，前端展示时区分颜色 |
| Few-shot 锚定 | LLM Prompt 包含 3 个已标注标准答案的示例（高分/中分/低分各一），防止评分漂移 |

**LLM 输出格式（供后端解析，前端展示时加工）：**

```json
{
  "summary_one_liner": "不超过50字的一句话总结",
  "summary_highlights": ["亮点1", "亮点2", "亮点3"],
  "summary_comparison": "与已有技术的对比（1-2句）",
  "weight_adjustment": "open_source_tool",
  "scores": {
    "business": {"value": 5, "confidence": 0.9, "reason": "GitHub 3天5k star，解决Agent协作痛点，市场信号极强"},
    "deploy": {"value": 4, "confidence": 0.85, "reason": "pip install即用，文档完善，但依赖Python 3.12+有迁移成本"},
    "performance": {"value": 4, "confidence": 0.7, "reason": "延迟指标优秀(<100ms)，但缺少大规模benchmark数据支撑"},
    "compatibility": {"value": 4, "confidence": 0.9, "reason": "与公司Agent业务方向直接匹配，Python技术栈兼容"}
  },
  "score_total": 4.35,
  "confidence_overall": 0.84,
  "recommend_level": "强烈推荐",
  "rag_context_used": [
    {"id": "abc123", "similarity": 0.87, "title": "上月推荐的XX多Agent框架"}
  ]
}
```

#### 验收标准

- [ ] 每条 curated 情报 100% 完成分析（不遗漏）
- [ ] N 条情报并行分析，总耗时 = 单条耗时（最长的） + 开销 < 3 分钟（假设 15 条）
- [ ] 评分一致性：同一情报重复评分 3 次，总分标准差 < 0.5
- [ ] 每个维度评分附带置信度和具体理由（非空）
- [ ] 权重类型判断准确率 ≥ 80%
- [ ] 单条分析失败不影响其他条，失败条目不阻塞后续流程

### F-04：RAG 历史对比增强

#### 用户故事

> 作为技术研究员，分析一条新情报时，我需要知道"这个我们是不是看过类似的？""上个月的同类项目现在怎样了？"——系统应该自动帮我关联。

#### 功能描述

在 Analyst（分析节点）处理每条情报前，先用该情报的 title + description 检索 ChromaDB 向量数据库中历史相似情报（top-5），将检索结果注入 LLM 的 Prompt 上下文，让 LLM 在分析时能：

- 对比新旧情报的异同
- 判断是否是对已有技术的改进/替代
- 追踪同一项目/技术的热度变化
- 标记高度重复的条目（建议降权）

**RAG 检索流程：**

```
新情报 title + description
  → text-embedding-3-small 向量化
  → ChromaDB 混合检索（向量相似度 0.7 + BM25 0.3）
  → 返回 top-5 相似历史情报
  → 注入 Analyst Prompt 作为参考上下文
```

**ChromaDB 索引结构：**

| 字段 | 内容 |
|------|------|
| id | 与 analyzed_items.id 一一对应 |
| document（检索用） | title + summary_one_liner + summary_highlights 拼接 |
| metadata | category_l1, category_l2, score_total, recommend_level, source, analyzed_at, url |

**检索策略：混合检索（Hybrid Search）**

| 方式 | 权重 | 优势 |
|------|------|------|
| 向量语义相似度 | 0.7 | 捕获语义相近的内容（如"多Agent框架"匹配到"多智能体协作系统"） |
| BM25 关键词匹配 | 0.3 | 保证专有名词精确匹配（如"LangGraph"不会匹配到"LangChain"的无关内容） |

**索引更新时机：** 每条情报分析完成后**立即**写入 ChromaDB，确保下一条情报即可检索到（同批次内后续条目的分析也能受益）。

#### 验收标准

- [ ] 每条分析中的情报 100% 触发 RAG 检索
- [ ] 向量检索 top-5 的召回中，至少 3 条与查询情报语义相关（人工抽样验证）

### F-10：定时调度引擎

#### 用户故事

> 作为系统管理员，系统应该每天自动在固定时间执行，我不需要手动去点任何按钮。

#### 功能描述

APScheduler 内嵌在 FastAPI 进程中，管理两个定时任务。

| 任务 | Cron 表达式 | 功能 |
|------|-----------|------|
| 采集分析任务 | `0 7 * * *`（每日 7:00） | 调用 LangGraph 图执行 Collect → Curate → Analyze → Edit，生成日报写入 DB |
| 推送任务 | `0 8 * * *`（每日 8:00） | 调用 Dispatcher Node 将日报推送到飞书 Bot + 飞书文档 |

**为什么分两个任务？**
- 7:00-8:00 之间为日报处理窗口（采集、筛选、LLM 分析），预期 15-25 分钟
- 8:00 准时推送，即使分析提前完成，也等到 8:00 推送（用户习惯每天早上 8 点收到）
- 如果 7:00 任务到 8:00 仍未完成（异常情况），8:00 推送任务检测到后标记本次日报为 `partial` 并推送已完成部分

#### 容错设计

| 场景 | 处理方式 |
|------|---------|
| 7:00 任务失败 | 记录错误日志，8:00 推送任务检测到无新日报时推送"今日日报生成失败，请检查系统"的告警消息 |
| 7:00 任务超时（到 8:00 未完成） | 推送任务标记日报为 `partial`，推送已完成的部分，并在消息中标注"⚠️ 部分数据，全量报告中" |
| FastAPI 进程重启 | APScheduler 随进程启动后自动恢复任务调度 |
| 手动触发与定时任务并发 | 后端加锁（数据库行锁或 Redis 锁），同一时间只允许一个流程运行 |

#### 验收标准

- [ ] 7:00 任务每日自动执行，误差 ±5 分钟
- [ ] 8:00 推送每日自动执行，误差 ±3 分钟
- [ ] 手动触发与定时任务不并发冲突
- [ ] 定时任务失败时管理员从 Web 页面可见错误日志
- [ ] FastAPI 重启后调度器自动恢复

## 6. 非功能需求

### 6.1 性能

| 指标 | 目标值 | 测量方式 |
|------|--------|---------|
| 采集阶段耗时 | < 60 秒（4 源并行） | 日志计时 |

| 全流程耗时 | < 25 分钟 | 日志计时 |
| Web 页面首次加载 | < 2 秒 | Lighthouse |
| API 检索响应 | < 1 秒（1000 条数据内） | API 响应时间 |
| 数据库写入 | 单条 < 50ms，批量 < 500ms | SQLAlchemy 日志 |

### 6.2 可用性

| 指标 | 目标值 |
|------|--------|
| 日报按时推送率 | ≥ 95%（月度统计） |
| Web 页面可用率 | ≥ 99%（排除计划维护） |
| 单信源故障时系统可用性 | 不受影响，其他信源正常 |

### 6.3 安全

| 需求 | 说明 |
|------|------|

### 6.4 可维护性

| 约束 | 说明 |
|------|------|

### 7.2 假设

| 假设 | 影响 |
|------|------|
| DeepSeek API 稳定可用，单次调用延迟 < 5 秒 | 如果不可用，分析阶段将失败 |

| 团队有飞书管理员权限，可创建飞书文档 | 否则文档推送不可用 |
| 用户使用 Chrome/Edge/Firefox 最新版本浏览器 | 不保证 IE 兼容 |

## 8. 附录

### 8.1 术语表

| 术语 | 说明 |
|------|------|
| Agent / 智能体 | 具有特定职责和工具的 LLM 驱动执行单元 |
| Node / 节点 | LangGraph 图中的处理单元，等同于一个 Agent |
| State / 状态 | LangGraph 中在节点间流转的共享数据对象 |
| RAG | 检索增强生成（Retrieval-Augmented Generation），分析时检索历史数据增强 LLM 上下文 |
| 四维评分 | Synapse_Rader 的核心评测体系：商业潜力 × 落地难度 × 性能指标 × 业务兼容性 |
| 置信度 | LLM 对自身评分的把握程度（0.0-1.0） |
| 上下文自适应权重 | 根据情报类型（开源工具/论文/产品动态）动态调整四个维度的权重 |
| ChromaDB | 嵌入式向量数据库，存储 analyzed_items 的向量化表示，为 RAG 提供检索能力 |
| Run ID | 每次日报执行流程的唯一标识，用于追踪和日志关联 |
